# Officer Naming — canonical old → new map (EU-57)

The single human-readable reference for officer role names: which army-metaphor names were
**retired**, what the **canonical** display name is now, and — just as important — which uses of the
old names are **intentional and must stay**. Read this whenever a name looks inconsistent before
"fixing" it.

## The one source of truth (do not duplicate)

The machine-readable map lives in [`orchestrator/officers.py`](../orchestrator/officers.py) as
`OFFICER_NAMES` (re-exported from `orchestrator.config`). Everything that shows an officer to a
human imports `OFFICER_NAMES` / `display()` from there — nothing else hard-codes a name. This doc
mirrors that map for humans; the regression suite (`tests/eu57_officer_naming_test.py`,
`tests/officer_rename_regression_test.py`) fails if the two ever drift apart.

## Old → new display names (the EU-17 / EU-23 / EU-40 rename)

| `general`        | The General        | **CTO** |
| `field_engineer` | Field Engineer     | **Dev Team Lead** |
| `inspector`      | Inspector General  | **Code Reviewer** |
| `adjutant`       | Adjutant           | **Engineering Manager** |
| `provost`        | Provost Marshal    | **Security Engineer** |
| `quartermaster`  | Quartermaster      | **Release Manager** |
| `sentinel`       | Sentinel           | **SRE** |
| `drillmaster`    | Drillmaster        | **Engineering Coach** |
| `scout`          | Scout              | **QA Engineer** |
| `scribe`         | Scribe             | **Technical Writer** |
| `soldiers`       | soldiers           | **engineers** |
| `pm`             | Product Manager    | Product Manager *(unchanged)* |
| `devops`         | DevOps             | DevOps *(unchanged)* |
| `test_engineer`  | Test Engineer      | Test Engineer *(unchanged)* |
| `liaison`        | *(new — EU-66)*    | **Mayor** |

The `liaison` officer (EU-66) is new — it has no retired army name. Its internal key is the stable
`liaison`; its human-facing display name, decided by the Commander, is **Mayor** (the inter-unit
ambassador / outward voice to the allied unit).

## What is intentional and MUST NOT be renamed

The rename retired the army metaphor **only for human-facing display names**. The following keep the
old vocabulary by design — changing them would break the system or destroy intended flavour:

1. **Internal keys / identifiers** — `scout`, `sentinel`, `drillmaster`, `provost`, `quartermaster`,
   etc. are immutable lookup keys (module names, role ids, config keys like `sentinel_enabled`, agent
   ids, audit kinds like `soldier_build`, the `<!-- SCRIBE:BEGIN -->` memory markers). They are NOT
   display names and never change. `display(key)` maps a key to its canonical name at the edge.
2. **Officer charter files** — `officers/*.md` are deliberately framed with the army metaphor
   (`> Army role: …`) as flavour, then mapped to the dev-team role. The filenames are the internal
   keys (`scout.md` = `scout`). These are the unit's character, not a leak.
3. **Historical changelog** — `ROADMAP.md` is an append-only record of what shipped *at the time*;
   its entries are dated history and are left verbatim, army names and all.
4. **The map's own definition** — `orchestrator/officers.py` documents the old → new mapping in its
   docstring; that is the one place the retired names legitimately appear in `orchestrator/`.

## Where the canonical names ARE enforced

`tests/officer_rename_regression_test.py` scans every `orchestrator/**/*.py` (except the SOT module)
and fails if any retired display name — full ("Provost Marshal") or bare persona ("the Inspector") —
is hard-coded into a prompt, label, or runtime string. Programmatic human-facing labels
(roster / cockpit board / group-room) must each resolve to `display(internal_key)`. The living unit
memory's log heading is generated by `orchestrator/memory.py` as the canonical
"_(Technical Writer-maintained — newest first)_".
